## 1. Побитовая парити с апстримом

```bash
python -m tlab_ued.parity --presets dr plr accel --num_updates 500
```

[`parity.py`](../src/tlab_ued/parity.py) импортирует апстримные `examples/maze_dr.py` и
`examples/maze_plr.py` из `third_party/jaxued`, запускает их и наш тренер **в одном процессе на
одном сиде**, перехватывает всё, что каждая сторона отдаёт в `wandb.log`, и диффает скалярные
записи. Требуемый результат — не «похожие кривые», а нулевой diff: совпадение до последнего бита.

### Почему это вообще возможно

JAX не берёт случайность из глобального состояния. Каждый вызов, которому нужен шум, получает
явный ключ, а новые ключи производятся из старого через `jax.random.split(key, n)`. Split
детерминирован: из одного ключа всегда получаются те же потомки, в том же порядке. Значит, вся
случайность прогона полностью определена начальным сидом **и последовательностью split-ов**.

Отсюда следствие, которое и делает проверку осмысленной: если наш код проходит по той же цепочке
split-ов, что апстримный, он получает ровно те же уровни, те же действия, ту же инициализацию
весов — и все метрики совпадают побитово. Ненулевой diff означает, что где-то шов срезан неверно.

### Как это ломается незаметно

```python
rng, rng_a, rng_b = jax.random.split(rng, 3)
```

Кажется безобидным разбить это на две строки, поменять местами `rng_a` и `rng_b` или взять
`split(rng, 2)` там, где апстрим брал 3, потому что третий ключ в этой ветке не используется.
Любое из трёх — новая цепочка ключей. Код читается идентично, тесты проходят, метрики выглядят
правдоподобно, а алгоритм уже другой: за 30000 апдейтов разошедшиеся ключи означают другие
уровни, другие траектории и другой итоговый solve rate.

Отсюда правило из [`CLAUDE.md`](../CLAUDE.md): тела веток сохраняют апстримную арность и порядок
`split` буквально, даже когда часть ключей в нашей версии не нужна. Это единственное, что отделяет
«воспроизвели бейзлайн» от «получили другой алгоритм, похожий на бейзлайн» — а если наши
DR/PLR/ACCEL отличаются от опубликованных чем-то, кроме имени, то бейзлайн, который мы бьём, не
тот, о котором говорит задание, и +0.18 над ним ничего не значит.

### Результат

Прогнано на A100 после завершения всех прогонов (на свободной карте — CPU-версия этой проверки
слабее):

```
parity[dr, seed 0] over 2 eval steps: IDENTICAL
parity[plr, seed 0] over 2 eval steps: IDENTICAL
parity[accel, seed 0] over 2 eval steps: IDENTICAL
```

Все три бейзлайна воспроизводят апстрим побитово. Это важно ещё и потому, что работа над SFL и
oracle трогала общие файлы (`scoring.py`, `teachers/base.py`, `logging_utils.py`): бейзлайны через
них не ходят, но всё сравнение обесценилось бы, если бы они сдвинулись.

Проверку нужно гонять после любой правки на пути обучения. Она стоит пары минут и ловит класс
ошибок, который иначе всплыл бы только как необъяснимо другие числа через сутки GPU-времени.

## 2. Инварианты, проверяемые кодом

Три ограничения задания не запоминаются, а падают в рантайме:

1. **Student заморожен.** `assert_student_frozen` запускается в начале каждого прогона и отвергает
   любое отклонение от апстримных гиперпараметров PPO, бюджета и `agent_view_size`. Флаг
   `--allow_student_changes` существует только для намеренных абляций и помечает прогон как
   испорченный.
2. **Eval-уровни только измеряют.** Не используются ни в обучении, ни в подборе гиперпараметров,
   ни как шаблоны для генерации.
3. **Архитектура политики не меняется.** Чекпоинты грузятся харнессом организаторов, который
   читает `loaded["params"]` в исходный `ActorCritic`. Состояние teacher'а может ехать в чекпоинте
   рядом; изменённое дерево `params` — провал сдачи. Проверяется каждым прогоном через
   немодифицированный апстримный `maze_plr.py --mode eval`.

`third_party/jaxued` вендорен на коммите `0f8f128` и не редактируется: это референс парити.

## 3. Как воспроизвести

```bash
git clone <этот репозиторий> && cd tlab_ued
bash scripts/bootstrap.sh
```

```bash
PY=/workspace/venvs/jaxued/bin/python

# один прогон
$PY -m tlab_ued.train --preset accel --seed 0 --out_dir /workspace/tlab_ued

# sweep, отсоединённый и возобновляемый
$PY -m tlab_ued.sweep --jobs sfl_oracle:0 sfl_accel_cheap:0 --out_dir /workspace/tlab_ued --wait

# из чего состоит курикулум (GPU не нужен)
$PY -m tlab_ued.level_diagnostics --preset accel

# что мутатор может произвести сам по себе, без агента (GPU не нужен)
$PY -m tlab_ued.level_diagnostics --preset accel --ladder --ladder_out results/mutation_ladder.json

# во что курикулум превратился на самом деле: буфер из чекпоинтов (GPU не нужен)
$PY -m tlab_ued.buffer_diagnostics --run sfl_accel_learnability --seed 0 --out results/buffer.json

# оценить чекпоинт на held-out уровнях
$PY -m tlab_ued.train --mode eval --checkpoint_directory checkpoints/sfl_oracle_learnability_level_bfs/0

# таблицы и графики из metrics.csv
python scripts/report.py --out_dir /workspace/tlab_ued

# тесты и побитовая сверка с апстримом
$PY -m pytest tests -q
$PY -m tlab_ued.parity --presets dr plr accel --num_updates 500
```

Полный прогон — 30000 апдейтов (~245M env-шагов), ~2.5 часа на A100 (девять параллельно под MPS).

## 4. Структура

```
src/tlab_ued/
  student.py      ЗАМОРОЖЕН - дословная копия апстримного PPO+LSTM
  teachers/       стратегии отбора уровней: dr.py, plr.py, accel.py, sfl_accel.py, sfl_oracle.py
  scoring.py      реестр score-функций
  oracle.py       обучаемая модель p(solve | level)
  levels.py       реестр генераторов и мутаторов
  level_diagnostics.py  BFS по генерируемым уровням
  train.py        teacher-агностичный цикл обучения, чекпоинты, протокол оценки
  parity.py       наш тренер против апстримного, тот же сид, диффом
  buffer_diagnostics.py BFS по буферу уровней, вынутому из чекпоинтов прогона
  analysis.py     metrics.csv -> таблицы и графики
```

Артефакты: `runs/<run>/<seed>/metrics.csv`, `checkpoints/<run>/<seed>/`,
`results/summary.md`, `results/figs/`.
